# 수학 교육 웹·앱 정밀 분석 방법

## 1. 분석 단위

기능 이름이 아니라 아래 6개 층으로 분해합니다.

~~~text
학습 목표
  ↓
수학 개념 / 관계
  ↓
사용자가 만지는 화면 객체
  ↓
입력 제스처와 도구 모드
  ↓
수학 상태 변화 / 제약 조건
  ↓
렌더링 · 저장 · 공유 · 평가
~~~

예를 들어 '선대칭'을 분석할 때 단순히 '뒤집기 버튼이 있다'로 끝내지 않습니다.

- 원본 도형 객체가 무엇인가
- 기준선이 별도 객체인가
- 도형 선택 → 기준선 선택의 2단계 상태 머신인가
- 결과 객체가 원본과 의존 관계를 갖는가
- 기준선을 움직였을 때 결과가 동적으로 갱신되는가
- 결과를 독립 객체로 복제하는가, 파생 객체로 유지하는가
- 실행 취소는 명령 단위인가 객체 변화 단위인가
- 직관적 조작과 정확한 수치 입력 사이의 균형은 어떤가

를 확인해야 합니다.

## 2. Craft Anything에서 가져온 분석 태도

Craft Anything은 원본을 Study하고, 만든 결과를 Check하며, 추측보다 증거를 남기는 구조를 강조합니다. 이 저장소에서는 다음처럼 변형합니다.

### 2.1 Study
- 공식 화면
- 공식 도움말/사용자 매뉴얼
- 공식 API 문서
- 공개 저장소
- 현재 서비스의 실제 동작
- 접근성 문서
- 저장/공유/과제 흐름

을 가능한 한 서로 교차 검증합니다.

### 2.2 Model

관찰을 내부 모델로 재구성합니다.

~~~text
Pointer / Keyboard / Touch
        ↓
Interaction Controller
        ↓
Tool / Gesture Interpreter
        ↓
Math Operation / Constraint
        ↓
Document State / Object Graph
        ↓
Derived Values
        ↓
2D / 3D / Formula / Table View
~~~

단, 내부 코드가 비공개라면 이 구조는 반드시 **[INFERRED]**로 표시합니다.

### 2.3 Compare

서비스 간 비교 기준은 '기능 개수'가 아닙니다.

- 같은 개념에 도달하기까지 필요한 조작 수
- 오류 조작을 막는 방식
- 자유 탐구와 정답 지향성의 비율
- 표현 간 연결 강도
- 화면 복잡도
- 초등학생이 명칭을 몰라도 조작 가능한지
- 교사가 활동을 만들어 재사용할 수 있는지
- 학생 결과를 회수할 수 있는지
- 모바일/터치에서 같은 의미가 유지되는지

를 비교합니다.

### 2.4 Extract

마지막에는 반드시 '우리 서비스에서 재사용 가능한 구조'로 바꿔 적습니다.

~~~ts
type MathObject = {
  id: string
  kind: 'point' | 'segment' | 'polygon' | 'fractionBar' | string
  props: Record<string, unknown>
  dependencies: string[]
}

type MathOperation = {
  type: string
  inputs: string[]
  parameters: Record<string, number | string | boolean>
}

type Representation = {
  objectId: string
  view: 'canvas2d' | 'scene3d' | 'formula' | 'table'
}
~~~

이 예시는 특정 서비스의 실제 구현이 아니라 비교 분석을 위한 공통 추상화입니다.

## 3. 화면 분석 체크리스트

### 전역 내비게이션
- 홈/도구/수업/자료/내 작업/공유/계정의 구분
- 학생과 교사의 정보 구조 차이
- 도구 진입까지의 클릭 수
- 기존 작업을 다시 찾는 경로

### 작업 화면
- 상단바: 문서명, 저장, 공유, 실행취소
- 좌측: 도구/객체/식 목록
- 중앙: 캔버스/그래프/3D 장면
- 우측: 속성/정보/검사기
- 하단: 입력 키패드/페이지/상태/재생
- 모달: 숫자 입력, 내보내기, 과제 제출

### 선택 상태
- hover
- selected
- multi-selected
- locked
- hidden
- disabled
- invalid
- derived/dependent

수학 앱에서는 선택 상태가 곧 '무엇을 다음 연산의 피연산자로 사용할지'를 결정하므로 일반 콘텐츠 앱보다 중요합니다.

## 4. 수학 상호작용 분석

### 조작 문법

| 문법 | 예 |
|---|---|
| Tool-first | '선분' 도구 → 점 A → 점 B |
| Object-first | 도형 선택 → 변환 메뉴 |
| Gesture-first | 항을 반대편으로 드래그 |
| Expression-first | 식 입력 → 자동 그래프 |
| Manipulative-first | 분수 조각을 캔버스로 끌어오기 |
| Simulation-first | 매개변수를 바꾸고 현상을 관찰 |

### 제약 조건
- 점이 선 위에서만 움직임
- 도형이 그리드/각도에 스냅
- 분수 조각이 같은 전체에 정렬
- 대수적으로 허용된 이동만 성공
- 3D 큐브가 격자 좌표에만 놓임

제약은 '자유를 제한하는 기능'이 아니라 수학 구조를 인터페이스에 내장하는 방식으로 봅니다.

### 피드백
- 즉시 결과
- 애니메이션
- 색 변화
- 스냅
- 진동/흔들림
- 수치 표시
- 유도선
- 음향/소니피케이션
- 힌트

피드백이 정답을 알려주는지, 관계를 인식하게 하는지 구분합니다.

## 5. 기술 구조 분석

### 공개 소스인 경우
실제 경로를 적고 폴더별 책임을 설명합니다.

### 비공개인 경우
다음 3개를 분리합니다.

1. 브라우저/공식 문서에서 확인 가능한 기술
2. 공식 API가 공개한 데이터 모델
3. 행동으로 추정한 내부 계층

근거 없는 프레임워크 추정은 하지 않습니다.

## 6. 상태 전이 표 작성법

| 현재 상태 | 입력 | 검증 | 다음 상태 | 결과 |
|---|---|---|---|---|
| idle | 뒤집기 선택 | - | await-object | 안내 표시 |
| await-object | 도형 클릭 | 객체 유형 확인 | await-axis | 도형 강조 |
| await-axis | 선 클릭 | 기준선 가능 여부 | committed | 반사 객체 생성 |
| await-axis | 빈 공간 클릭 | 실패 | await-axis | 변화 없음 |
| committed | undo | history pop | 이전 상태 | 생성 객체 제거 |

이 표는 실제 내부 코드가 아니라 **관찰된 UX를 상태 머신으로 설명한 것**일 수 있습니다.

## 7. 교육적 분석

- 탐구 가능한가
- 결과만 계산하는가
- 여러 표현을 오갈 수 있는가
- 예상 → 조작 → 관찰 → 설명 흐름이 가능한가
- 학생이 자신의 전략을 남길 수 있는가
- 교사가 문제 조건을 고정할 수 있는가
- 학생마다 다른 해가 허용되는가
- 산출물을 공유/비교할 수 있는가

## 8. 서비스 하나당 최소 산출물

- 화면/페이지 지도
- 핵심 버튼과 역할
- 핵심 사용자 흐름 3개 이상
- 수학 객체/연산 모델
- 상태 전이 또는 이벤트 흐름
- 저장/공유 구조
- 기술 구조
- 공개 소스 경로 또는 비공개 표시
- 장점 3개 이상
- 구조적 한계 3개 이상
- 가져올 패턴
- 피해야 할 패턴
- 추가 검증 목록
- 공식 출처
